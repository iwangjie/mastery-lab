# 掌握场景编写指南

这份指南用于约束后续新增题目，避免仓库退化成资料堆、玩具项目堆或 AI 生成文件堆。

## 编写顺序

新增一个训练内容时，按这个顺序：

1. 先在 `topics/` 中确认课题和能力节点。
2. 再在 `breakdowns/` 中写问题拆解。
3. 然后在 `problems/` 中创建可运行或可交付的掌握场景。
4. 最后补验证方式和复盘问题。

不要先生成一堆代码再倒推它训练什么。这样很容易制造复杂度，但不一定制造掌握。

## 合格题目的最低标准

一个掌握场景至少要满足：

- 有真实失败现场，而不是只有知识点。
- 有明确目标能力，而不是泛泛地“练习某技术”。
- 有限制条件，防止绕开训练目标。
- 有一个以上常见失败路径。
- 有验证方式，最好能脚本化。
- 有复盘问题，要求解释底层机制。
- 有至少两个变体方向，用来检查迁移。

## 好题和坏题

坏题：

```text
做一个 Todo App，使用 React、TypeScript、Tailwind。
```

问题：它没有说明要掌握什么，也没有真实失败模式。AI 很容易直接生成一个能跑的项目，人类可能什么都没掌握。

好题：

```text
一个筛选列表在用户快速切换条件时偶尔显示旧数据。
要求定位请求竞态，保留加载态和错误态，不能用固定延时掩盖问题。
验证方式：自动化测试模拟乱序响应，最终 UI 必须显示最后一次请求的数据。
```

它训练的是异步状态、请求生命周期和竞态判断，而不是“写一个页面”。

## 控制复杂度

题目复杂度应该来自真实约束，不来自无意义堆料。

允许增加：

- 多个协作者。
- 历史包袱。
- 缺失信息。
- 失败日志。
- 模糊需求。
- 部分错误的 AI 建议。

谨慎增加：

- 大量无关文件。
- 多个框架混用。
- 与目标能力无关的配置。
- 纯装饰性 UI。
- 难以验证的主观要求。

## 提示设计

提示要帮助学习者继续观察，而不是替他完成。

推荐：

```text
Hint 1: 看看远程分支和同事本地分支的提交图有什么不同。
Hint 2: 关注 rebase 后 commit identity 是否改变。
Hint 3: 可以从仍保留旧提交的 clone 中取回目标提交。
```

不推荐：

```text
运行 git remote add teammate ../teammate，然后 cherry-pick 某个提交。
```

完整操作只能作为最后一级提示，且必须要求学习者解释为什么安全。

## AI 生成后的审查清单

AI 生成题目后，必须检查：

- 这题是否有单一清晰的主目标能力？
- 验证脚本是否真的会在初始状态失败？
- 验证脚本是否能在正确修复后通过？
- 是否存在绕过目标能力的捷径？
- 文件和需求是否有无关复杂度？
- 复盘问题是否要求解释机制，而不是复述命令？
- 变体是否真的改变了表面场景？

## 文件命名

掌握场景目录建议：

```text
problems/<topic>/<number>-<short-name>/
```

对应问题拆解：

```text
breakdowns/<topic>/<number>-<short-name>.md
```

编号只表示同一课题下的排序，不表示绝对难度。
