# 框架：课题、能力图谱、问题拆解、掌握场景

## 设计假设

第一阶段不做复杂平台，不做大而全课程，也不追求一次性覆盖所有技术。先把可复制的训练结构搭起来，让任何课题都能被拆成能力、问题、验证和复盘。

## 一、课题

`课题` 是一个长期掌握方向，不等于某个教程标题。

好的课题应该能回答：

- 它解决哪类真实问题？
- 专家在这个领域会做哪些判断？
- 常见失败模式是什么？
- 哪些底层概念必须通过实践才能真正理解？
- 哪些结果可以作为掌握证据？

示例：

- Git 协作：合并、变基、冲突、恢复、远程历史、团队约定。
- 前端工程：布局、状态、异步、性能、可访问性、构建、调试。
- 反汇编：指令、调用约定、栈、寄存器、控制流、混淆、补丁。
- 软件设计：TDD、DDD、面向对象、边界、依赖、演进、可测试性。

## 二、能力图谱

`能力图谱` 把课题拆成可训练的能力节点。每个节点不只写概念，还要写表现和失败模式。

推荐格式：

```text
能力节点
  -> 真实任务
  -> 底层概念
  -> 常见错误
  -> 可观察信号
  -> 验证方式
  -> 可生成的掌握场景
```

以 Git 为例：

```text
公共分支历史
  -> 判断什么时候不能 rebase
  -> commit identity、remote refs、force push、reflog
  -> 把公共分支 rebase 后强推，覆盖队友提交
  -> 远程分支提交消失，本地和队友分支分叉
  -> 能恢复提交、解释原因、给出团队防线
  -> 制造一个被错误 force push 破坏的仓库
```

## 三、问题拆解

`问题拆解` 是课题和掌握场景之间的桥。它回答：这个问题为什么值得做，它到底训练哪种判断，学习者可能如何失败，什么证据能证明掌握。

没有问题拆解，AI 很容易生成“看起来像项目”的练习，但它可能只是在堆文件、堆需求、堆复杂度。问题拆解负责把复杂度约束到目标能力上。

一个合格的问题拆解应该包含：

- 目标能力：这题主要训练什么，不训练什么。
- 真实来源：现实中什么场景会出现这种问题。
- 关键判断：专家会观察哪些信号。
- 底层机制：必须理解哪些概念才能稳妥解决。
- 失败路径：初学者或 AI 容易给出哪些危险方案。
- 验证证据：什么结果能证明不是碰巧做对。
- 升级变体：如何改变表面场景来测试迁移。

## 四、掌握场景

`掌握场景` 是本项目的核心。它不是普通练习题，而是一个带有现场、约束、陷阱和验证的实践问题。

一个合格的掌握场景必须包含：

- 背景：为什么这个问题会在真实工作中出现。
- 任务：人类需要交付什么。
- 限制：不能用哪些偷懒方式，必须保留哪些约束。
- 失败模式：这个场景故意考察什么常见错误。
- 验证：如何证明问题解决了。
- 复盘：解决后必须解释什么机制。
- 变体：下一轮如何升级或迁移。

## 五、难度等级

不要用“初级/中级/高级”这种模糊标签。建议用人的独立程度和迁移能力定义难度：

| 等级 | 名称 | 判断标准 |
| --- | --- | --- |
| L0 | 知道 | 能说出概念，但不能稳定解决问题 |
| L1 | 跟做 | 给步骤能完成，离开步骤容易失败 |
| L2 | 修复 | 能在单一故障中独立定位并修复 |
| L3 | 诊断 | 能在混合故障中判断优先级和因果 |
| L4 | 设计 | 能提前设计约束，避免问题发生 |
| L5 | 迁移 | 能把原理迁移到新场景，并能出题考别人 |

## 六、证据系统

不要用“我感觉懂了”作为完成标准。每个掌握场景都必须有证据。

常见证据：

- 命令输出
- 测试结果
- 运行截图
- 最终代码 diff
- 调试记录
- 设计取舍说明
- 事故复盘
- 对反例的解释

证据应该证明三件事：

1. 结果正确。
2. 过程没有绕过目标能力。
3. 人能解释底层机制和边界。

## 七、复盘问题

每个场景结束后至少回答：

- 我最初怎么判断问题范围？
- 哪个信号最关键？
- 我走过哪些错误路径？
- 这个问题真正考察的底层机制是什么？
- 如果 AI 给出一个看似正确但有风险的方案，我怎么审查？
- 下次我会如何更快发现同类问题？
- 我能不能设计一个变体来测试别人？
