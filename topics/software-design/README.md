# 课题：软件设计与工程实践

## 为什么值得掌握

TDD、DDD、面向对象、微服务、开闭原则、组合优于继承这些词大家都听过。难点不在于复述定义，而在于业务变化快、约束复杂、代码已有历史包袱时，如何判断哪些理论能落地，哪些只是增加成本。

这个课题不训练口号，训练取舍。

## 能力图谱草案

| 能力节点 | 真实任务 | 底层概念 | 常见错误 | 掌握场景方向 |
| --- | --- | --- | --- | --- |
| TDD | 用测试驱动一个小变更 | red/green/refactor、test seam | 为了测试改坏设计 | 给遗留代码加行为保护后改需求 |
| DDD | 找出业务边界和模型语言 | bounded context、aggregate、ubiquitous language | 把表结构当领域模型 | 给混乱需求拆上下文 |
| 面向对象 | 在变化点上选择组合或继承 | polymorphism、composition、coupling | 为抽象而抽象 | 给支付策略迭代需求，约束修改范围 |
| 微服务 | 判断是否应该拆服务 | coupling、data ownership、latency | 把组织问题伪装成技术拆分 | 给一个慢迭代模块，评估拆分成本 |
| 设计原则 | 在真实约束里使用原则 | cohesion、dependency direction | 套原则口号 | 给一个需求变更，比较两种设计 |

## 第一批掌握场景建议

- 遗留订单折扣逻辑：先写 characterization tests，再改需求。
- 支付策略变化：比较继承树和组合策略的后续修改成本。
- “是否拆微服务”评审：要求给出数据所有权、部署、失败模式和团队边界。
- DDD 建模：从客服、财务、履约三方冲突语言里拆 bounded context。
