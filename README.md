# Mastery Lab（掌握实验室）

Mastery Lab 是一个以问题驱动掌握的开源学习框架。

这个仓库不是教程库，也不是资料索引。它的目标是把 AI 时代的学习重新组织成一套以人类为主导、以问题为入口、以证据证明掌握的实践框架。

核心判断：

- 写代码、写文档、生成项目已经变得廉价。
- 真正稀缺的是：人类能否判断 AI 生成物是否正确，能否定位问题，能否解释底层机制，能否在陌生场景里迁移。
- 因此这里不追求“看过多少资料”，而追求“解决过哪些足够接近真实工作的掌握场景”。

## 核心单位

这个项目使用四个基本单位：

1. `课题`：一个需要长期掌握的能力领域，例如 Git 协作、前端工程、反汇编、TDD、领域建模、微服务设计。
2. `能力图谱`：把课题拆成专家真实工作时会调用的动作、判断、失败模式和底层概念。
3. `问题拆解`：解释一个掌握场景到底考什么、为什么这样设计、有哪些失败路径和验证证据。
4. `掌握场景`：由 AI 或人类故意制造的实践问题。它必须有真实约束、可验证结果、常见陷阱和复盘要求。

“掌握场景”是这个项目里对“问题”的暂定命名。它比练习题更接近真实工作，比项目更小，比教程更重视诊断、取舍和反馈。

## 工作循环

```text
选择课题
  -> 拆能力图谱
  -> 做问题拆解
  -> 设计掌握场景
  -> 人类独立解决
  -> 用证据验证
  -> 复盘底层机制
  -> 生成变体或升级难度
```

AI 的主要职责不是直接给答案，而是：

- 制造足够逼真的问题现场。
- 设计失败模式和验证门槛。
- 在解题后追问、审查和生成变体。
- 帮人类把一次解决经验沉淀成可迁移的模型。

人类的主要职责是：

- 判断要掌握什么。
- 亲自解决问题。
- 解释自己的判断依据。
- 接受验证和复盘。
- 决定下一轮训练方向。

## 仓库结构

```text
docs/                  框架、方法、研究依据、AI 协作协议
templates/             课题、掌握场景、复盘记录模板
topics/                各课题的能力图谱和训练路线
breakdowns/            掌握场景的问题拆解和设计意图
problems/              可运行或可交付的掌握场景
tools/                 仓库检查、场景冒烟测试等辅助工具
prompts/               AI 生成、审查、复盘掌握场景的 prompt
```

第一版已经放入一个 Git 协作场景：

```bash
cd problems/git/001-public-rebase-damage
./setup.sh
```

它会生成一个被错误 `force push` 破坏过的本地协作现场。人的任务不是背 Git 命令，而是恢复被覆盖的队友提交，并解释为什么公共分支 rebase 会造成协作风险。

当前仓库检查：

```bash
node tools/check-links.mjs
./tools/smoke-git-scenario.sh
./tools/smoke-ruby-scenario.sh
```

## 使用方式

1. 先读 [docs/00-vision.md](docs/00-vision.md)，确认这个项目解决的不是“资料太少”，而是“问题太少”。
2. 再读 [docs/01-framework.md](docs/01-framework.md)，了解课题、能力图谱、掌握场景和证据系统。
3. 用 [templates/topic.md](templates/topic.md) 创建一个新课题。
4. 用 [templates/problem-breakdown.md](templates/problem-breakdown.md) 先拆清楚问题。
5. 用 [templates/mastery-scenario.md](templates/mastery-scenario.md) 创建掌握场景。
6. 解题后用 [templates/debrief.md](templates/debrief.md) 记录复盘。
7. 新增题目前读 [docs/05-authoring-guide.md](docs/05-authoring-guide.md)，避免生成无效复杂度。

## 判断是否真的掌握

一个人“掌握”某能力，至少要能做到：

- 在真实约束下解决相关问题，而不是只复述概念。
- 发现 AI 或他人方案中的关键错误。
- 解释问题背后的机制和边界。
- 在换一个表面场景后仍能迁移。
- 能设计一个新问题来测试别人是否掌握。
